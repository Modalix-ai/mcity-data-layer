# וורדפרס ו-JetEngine למי שבא מ-React ו-TS

מדריך אוריינטציה, צעד אחר צעד. מיועד למפתח ה-data/backend שמכיר API, SQL/NoSQL ו-TypeScript, ואין לו ניסיון בוורדפרס.

**איך לקרוא:** כל שלב בנוי על הקודם. בסוף יש תרגיל ליום הראשון.
**סימון:** ⚠️ = לא אומת. צריך לבדוק בגרסה האמיתית או מול מפתח WP.

---

## שלב 0. התמונה הגדולה

וורדפרס הוא **מונוליט שמרנדר HTML בשרת** (PHP) ומחובר למסד MySQL או MariaDB. אין בו SPA ואין build בצד לקוח. כל בקשה מייצרת HTML מחדש (או מגיעה ממטמון).

```
דפדפן
  │  GET /c/modiin/
  ▼
מטמון עמודים (LiteSpeed)  ── יש? מחזיר HTML מוכן
  │  אין
  ▼
PHP: ליבת וורדפרס
  ├─ טוען תוספים (plugins) ותבנית (theme)
  ├─ ממפה כתובת לשאילתה (rewrite)
  ├─ מריץ שאילתה על MySQL (WP_Query)
  └─ בוחר תבנית ומרנדר HTML
        (אצלנו: תבניות Elementor + רכיבי JetEngine)
```

**מקבילה בעולם שלך:** Next.js עם SSR, בתוספת CMS (כמו Strapi) ובתוספת מסך ניהול, הכל בחבילה אחת ובשפה אחת.

**הערה חשובה:** אפשר להשתמש בוורדפרס כ-headless (REST API ופרונט ב-React). **זה לא המודל אצלנו.** העיצוב נבנה ב-Elementor בתוך וורדפרס. לא לערבב בין השניים.

## שלב 1. מסד הנתונים

כל התוכן בוורדפרס יושב בקבוצה קטנה של טבלאות. מי שמכיר SQL יתפוס אותן מהר.

| טבלה | מה בה | מקבילה |
|---|---|---|
| `wp_posts` | **כל סוגי התוכן**: כתבות, עמודים, תמונות, ועוד. עמודה `post_type` מבדילה ביניהם | טבלה אחת גדולה עם discriminator |
| `wp_postmeta` | שדות מותאמים לכל פוסט: זוגות `meta_key` ו-`meta_value` | **EAV** (entity-attribute-value) |
| `wp_terms`, `wp_term_taxonomy`, `wp_term_relationships` | טקסונומיות: קטגוריות, תגיות, אזורים וקשרים לפוסטים | tags ו-many-to-many |
| `wp_termmeta` | שדות מותאמים למונח (למשל לאזור) | |
| `wp_users`, `wp_usermeta` | משתמשים ושדות שלהם | |
| `wp_options` | הגדרות האתר (מפתח וערך) | config table |

**עמודות עיקריות ב-`wp_posts`:** `ID`, `post_title`, `post_content`, `post_excerpt`, `post_status`, `post_name` (ה-slug), `post_type`, `post_date`, `post_author`, `post_parent`.

**שני דברים שחשוב להבין:**
1. **שדה מותאם הוא שורה ב-`wp_postmeta`, לא עמודה.** אין סכמה קשיחה. להוסיף שדה לא דורש migration. מצד שני, כל ערך הוא מחרוזת, ושאילתה על כמה שדות יוצרת joins.
2. אין foreign keys אמיתיים. קשר בין פוסטים הוא בדרך כלל ID שמור כערך.

### איך זה נראה כ-TypeScript

כך נראית כתבה אצלנו (לפי חוזה הנתונים), עם הערה מאיפה כל חלק מגיע:

```ts
type Scope = 'national' | 'local';

interface News {
  // wp_posts
  id: number;                    // ID
  title: string;                 // post_title
  slug: string;                  // post_name
  status: 'draft' | 'pending' | 'future' | 'publish'; // post_status
  date: string;                  // post_date

  // wp_postmeta (שדות מותאמים)
  lead: string;
  scope: Scope;
  article_type: 'news' | 'expert_article' | 'promoter_article' | 'converted_answer';
  canonical_area?: number;       // מזהה מונח

  // wp_term_relationships (טקסונומיות)
  area: string[];                // slugs של אזורים
  section: string[];
}
```

חוזה הנתונים שלנו הוא בעצם **ה-interfaces של הפרויקט**. המעצב מחבר תבניות לשמות האלה, כמו שקומפוננטה מחוברת ל-props.

## שלב 2. סוגי תוכן, סטטוסים ותפקידים

**Post type (סוג תוכן):** ערך בעמודה `post_type`. ברירות המחדל: `post` (כתבה), `page` (עמוד), `attachment` (קובץ מדיה).
**CPT (Custom Post Type):** סוג תוכן שאנחנו מגדירים: `news`, `expert`, `question`, `banner`, `event_links`. כל CPT מקבל כתובות, מסך ניהול ושאילתות משלו.

**סטטוסים של פוסט (`post_status`):**

| סטטוס | משמעות | קשור לדרישות הלקוח |
|---|---|---|
| `draft` | טיוטה | כתב יוצר טיוטה |
| `pending` | ממתין לעורך | עורך מאשר |
| `future` | מתוזמן לפרסום | תזמון פרסום |
| `publish` | מפורסם | |
| `trash` | באשפה | |

**תפקידים (roles):** RBAC מובנה, כולל רשימת capabilities לכל תפקיד.

| תפקיד | מה הוא יכול |
|---|---|
| Contributor | יוצר טיוטה, **לא מפרסם** (שולח לאישור) |
| Author | מפרסם את הפוסטים שלו |
| Editor | מפרסם ומנהל את כל התוכן |
| Administrator | הכל, כולל הגדרות ותוספים |

זה מתאים כמעט כמו שהוא לדרישת הלקוח: **כתב ← עורך ← מנהל.**

## שלב 3. טקסונומיות

טקסונומיה היא **דרך לסווג פוסטים**. כל ערך בתוכה הוא "מונח" (term).

- **היררכית** (כמו קטגוריות): למונח יש אב.
- **שטוחה** (כמו תגיות): בלי היררכיה.

אצלנו: `area` (14 מונחים, שטוחה), `section` (מדורים), `index` (תחומי מומחים). כל אחת מוצמדת ל-CPT אחד או יותר.

**מקבילה:** שדה tags מרובה ערכים, עם טבלת קישור (many-to-many) ועם כתובת ארכיון אוטומטית לכל ערך. **הכתובת האוטומטית היא הסיבה שבחרנו טקסונומיה לאזורים:** `/c/modiin/` נוצרת מעצמה.

## שלב 4. מחזור חיי בקשה: מכתובת ל-HTML

כך וורדפרס מגיע מכתובת ל-HTML. זה המקביל ל-router ול-layouts אצלך:

1. **Rewrite rules:** טבלת חוקים שממירה כתובת לפרמטרים של שאילתה. `/c/modiin/` הופך ל"ארכיון של טקסונומיה `area`, מונח `modiin`". המקביל: הגדרת routes.
2. **Main query:** וורדפרס מריץ שאילתה אוטומטית לפי הפרמטרים (`WP_Query`).
3. **Template hierarchy:** וורדפרס בוחר תבנית לפי סוג הדף: עמוד בית, פוסט בודד של CPT, ארכיון של CPT, ארכיון של טקסונומיה, ועוד.
4. **The Loop:** התבנית עוברת על תוצאות השאילתה ומדפיסה כל אחת. המקביל: `results.map(item => <Card />)`.

**אצלנו שלב 3 מוחלף:** Elementor Pro Theme Builder מחליט איזו תבנית מוצגת לפי **תנאי תצוגה** (למשל "ארכיון של הטקסונומיה `area`"), ולא לפי שם קובץ.

**דבר שכדאי לדעת:** אחרי שינוי של חוקי כתובות, צריך **לשמור מחדש את הגדרות הקישורים הקבועים** (Settings, Permalinks, Save). בלי זה הכתובת החדשה מחזירה 404. זו אחת הבעיות הנפוצות ביותר.

## שלב 5. WP_Query: שפת השאילתות

`WP_Query` הוא ה-ORM של וורדפרס. מקבל מערך פרמטרים ומחזיר פוסטים.

השאילתה של דף אזור, "5 הכתבות המקומיות האחרונות של מודיעין":

```php
$q = new WP_Query([
  'post_type'      => 'news',
  'post_status'    => 'publish',
  'posts_per_page' => 5,
  'orderby'        => 'date',
  'order'          => 'DESC',
  'meta_query'     => [[ 'key' => 'scope', 'value' => 'local' ]],
  'tax_query'      => [[ 'taxonomy' => 'area', 'field' => 'slug', 'terms' => 'modiin' ]],
]);
```

**באותו עולם שלך, זה מקביל ל:**

```ts
db.news.find({
  status: 'published',
  scope: 'local',
  area: { $in: ['modiin'] },
}).sort({ date: -1 }).limit(5);
```

**מה קורה בפועל ב-SQL:** `wp_posts` עושה JOIN ל-`wp_postmeta` (בשביל `scope`) ול-`wp_term_relationships` (בשביל `area`). עם כמה מאות מומחים וכתבות זה מהיר. עם מאות אלפי כתבות (ההיסטוריה של האתר הישן) צריך לשים לב לשאילתות עם הרבה `meta_query`.

**אנחנו לא נכתוב `WP_Query` ביד ברוב המקרים.** JetEngine בונה אותה לנו בממשק (שלב 8).

## שלב 6. Hooks, תוספים ועיצוב (theme)

**Hooks** הם מערכת האירועים של וורדפרס, ובעזרתם מרחיבים אותו בלי לשנות את הליבה.
- **Action:** "משהו קרה, תריצו קוד" (כמו event listener). דוגמה: כתבה נשמרה.
- **Filter:** "קחו ערך, שנו אותו והחזירו" (כמו middleware או reducer). דוגמה: שנו את ה-`rel` של קישור.

**Plugin:** חבילת PHP שנטענת בכל בקשה ומשתמשת ב-hooks. **Theme:** שכבת התבניות. אצלנו Elementor Pro מחליף את רוב העבודה של ה-theme.
**`mu-plugin`:** תוסף שנטען תמיד ולא ניתן לכיבוי ממסך הניהול. מתאים ללוגיקה של הפרויקט.

**השוואה זהירה:** תוסף הוא לא npm package מבודד. כל התוספים חיים באותו תהליך, יכולים להתנגש, ואין sandbox.

## שלב 7. Elementor

**Elementor** הוא בונה עמודים חזותי. **המעצב בונה בו את ה-UI.**

דברים שחשוב להכיר:
- **פריסת העמוד נשמרת כ-JSON** בשדה `_elementor_data` ב-`wp_postmeta`. עץ של widgets. (כך אפשר לקרוא ולשכפל פריסות.)
- **Theme Builder (Elementor Pro):** מאפשר לבנות תבנית של Header, Footer, פוסט בודד, וארכיון, ולהחיל אותה לפי **תנאי תצוגה**.
- **Dynamic Tags:** "חורים" בתבנית שמתמלאים בערך משדה. המקביל: `{item.title}` ב-JSX.

## שלב 8. JetEngine: איפה הוא נכנס

JetEngine הוא תוסף של Crocoblock, שנותן **ממשק להגדיר מבנה נתונים ושאילתות, ולחבר אותם ל-Elementor.** הוא לא מחליף את Elementor ולא את ליבת וורדפרס. הוא יושב באמצע.

**מקבילה:** כלי מסוג Strapi או Directus (בונה סוגי תוכן בממשק) בצירוף שכבת תצוגה ושאילתות.

### השכבות שלו

המסד המאומת מדף הסקירה הרשמי של Crocoblock. מה שלא נאמר שם מסומן ⚠️.

| שכבה | מה היא עושה | המקבילה שלך |
|---|---|---|
| **Custom Post Types** | מגדיר סוגי תוכן עם שדות | הגדרת model |
| **Meta Boxes ושדות** | קבוצות שדות. 20 סוגי שדות, חלים על פוסטים, עמודים, משתמשים, מונחים ועוד | שדות ב-schema |
| **Taxonomies** | טקסונומיות, אפשר היררכיות | tags |
| **Custom Content Types (CCT)** | **טבלה נפרדת בבסיס הנתונים**, שורה לכל פריט. בדף כתוב שזה משפר ביצועים באתרים גדולים | טבלת SQL אמיתית עם עמודות |
| **Relations** | קשרים: אחד לאחד, אחד לרבים, רבים לרבים. בין CPT, CCT, מונחים ומשתמשים | foreign keys ו-join tables |
| **Options Pages** | עמודי הגדרות עם שדות שחלים על כל האתר | config table |
| **Query Builder** | בונה שאילתות בממשק: פוסטים, CCT, מונחים, משתמשים, תגובות, מוצרים, וטבלאות SQL | ORM query builder |
| **Listing Item + Listing Grid** | מעצבים כרטיס אחד (Listing Item) ב-Elementor, וה-Listing Grid מריץ שאילתה ומציג את הכרטיס לכל תוצאה | `results.map(<Card />)` |
| **Dynamic widgets ו-Dynamic Tags** | Dynamic Field, Link, Image, Terms ועוד. מציגים ערך משדה | `{item.field}` |
| **Dynamic Visibility** | מציג או מסתיר אלמנט לפי תנאי | `condition && <X />` |
| **מודולים נוספים** | Profile Builder, Data Stores, REST API, Components, Glossaries ועוד | |

⚠️ **לא נאמר בדף הסקירה:** איפה JetEngine שומר את ההגדרות, וכיצד מייצאים ומייבאים אותן. זו שאלה חשובה (שאלה 3 ברשימת השאלות), כי אם ההגדרות רק במסד הנתונים, אין להן גרסאות ב-git.

⚠️ **טפסים ופילטרים** (JetFormBuilder, JetSmartFilters, JetSearch) הם תוספים נפרדים של Crocoblock. ידוע לי שהם קיימים, ולא אימתתי אותם מול התיעוד. צריך לבדוק איזה מהם מותקן.

### CPT או CCT: ההחלטה שמחכה לנו

| | CPT | CCT |
|---|---|---|
| איפה נשמר | `wp_posts` ו-`wp_postmeta` | טבלה נפרדת |
| כתובות, SEO, תבניות Theme Builder | **מובנה** | ⚠️ מוגבל, לבדוק |
| מתאים ל | תוכן שמוצג בציבור וצריך SEO | נתונים בהיקף גדול או נתונים פנימיים |

**הצעה ראשונית (לאמת מול מפתח WP):**
- `news`, `expert`, `question` (תשובות מתפרסמות): **CPT.** צריכים כתובות ו-SEO.
- `lead` (פניות): אפשר לשקול **CCT**, כי זה נותן טבלה עם עמודות נפרדות, בניגוד לגוש הטקסט הישן שהלקוח התלונן עליו.

## שלב 9. איך הכל מתחבר: הולכים על `/c/modiin/`

הדוגמה המלאה לדף אזור, מקצה לקצה:

1. **הדפדפן** מבקש `/c/modiin/`.
2. **LiteSpeed Cache** בודק אם יש HTML שמור. אם כן, מחזיר אותו וזהו.
3. אם לא, **PHP** נטען. הטקסונומיה `area` רשומה עם `rewrite slug = c`, ולכן הכתובת מזוהה כארכיון של המונח `modiin`.
4. **Elementor Theme Builder** מוצא תבנית עם התנאי "ארכיון של `area`" ומחיל אותה.
5. בתבנית יש כמה **Listing Grids**, אחד לכל קטע (חדשות, מומחים ועוד). לכל אחד מחובר **Query** מ-Query Builder: סוג `news`, `scope=local`, אזור = האזור הנוכחי, 5 פריטים, מיון לפי השיבוץ.
6. כל תוצאה מרונדרת דרך **Listing Item** (הכרטיס), עם **Dynamic Fields** שמחוברים לשדות (`title`, `lead`, תמונה).
7. **HTML מוכן** חוזר לדפדפן, ו-LiteSpeed שומר אותו.

**מי אחראי על מה:**

| שלב | אחראי |
|---|---|
| הגדרת CPTs, שדות וטקסונומיות (שלב 1 עד 3) | **אנחנו** |
| ה-Queries (שלב 5) | **אנחנו מגדירים, מפתח WP מחבר** (לסגור, שאלה 35) |
| תבניות, Listing Items, עיצוב (שלב 4 ו-6) | **המעצב / מפתח WP** |
| החוזה בין השכבות | **שמות השדות בחוזה הנתונים** |

## שלב 10. מתי כותבים קוד ומתי מגדירים

**ברירת מחדל: להגדיר בממשק, לא לכתוב קוד.** JetEngine אמור לכסות את רוב הצרכים.

**מה כנראה ידרוש קוד (תוסף משלנו, למשל `mcity-core`):**

| צורך | למה |
|---|---|
| שיבוץ דף הבית לפי אזור (`home_main`, `home_secondary`) | לוגיקה ושדות על מונח האזור |
| `canonical_area` ב-SEO | קישור לתוסף ה-SEO |
| `rel="sponsored"` לפי `is_paid` | filter על קישורים |
| מעבר סטטוס כתבה (טיוטה, ממתין, מפורסם) והכללים שלו | workflow |
| טוקן גישה לשאלות במקום מזהה | אבטחה (החלטה 30) |
| חסימת פרסום כרטיס מומחה בלי שדות חובה | validation |
| המרת תשובה לכתבה | פעולה באדמין |
| חוקי כתובות מיוחדים | rewrite |

**כלל אצבע:** מה שאפשר לבנות ב-JetEngine בלי קוד, נבנה שם. מה שדורש לוגיקה ובדיקות, נכתב בתוסף שלנו, עם git.

## שלב 11. PHP ל-TypeScript developer, בחמש דקות

| TS | PHP |
|---|---|
| `const x = 1` | `$x = 1;` |
| `{ a: 1 }` (אובייקט) | `['a' => 1]` (מערך אסוציאטיבי) |
| `[1, 2]` | `[1, 2]` |
| `obj.method()` | `$obj->method()` |
| `Class.staticFn()` | `Class::staticFn()` |
| `a + b` (חיבור מחרוזות: `+`) | `$a . $b` (חיבור מחרוזות: נקודה) |
| `fn = (x) => x + 1` | `fn($x) => $x + 1` |
| `import` | `use` או `require` |
| `console.log(x)` | `error_log(print_r($x, true))` |

**ההבדל הגדול:** ב-PHP שורה קוראת לשורה, בלי async. כל בקשה רצה מההתחלה ונגמרת. אין מצב משותף בין בקשות, חוץ ממסד הנתונים והמטמון.

**פונקציות וורדפרס שכדאי להכיר:** `get_post_meta()`, `update_post_meta()`, `get_the_terms()`, `add_action()`, `add_filter()`, `register_post_type()`, `register_taxonomy()`.

## שלב 12. סביבת עבודה וכלים

| כלי | לשם מה |
|---|---|
| **סביבת staging** | לעבוד על העתק, לא על האתר החי. (שאלה 1) |
| **WP-CLI** | שורת פקודה לוורדפרס, למשל `wp post list --post_type=news` |
| **Query Monitor** (תוסף) | מראה אילו שאילתות רצו, אילו hooks, ואיזו תבנית נבחרה. **מומלץ מאוד לדיבוג** |
| **REST API** | `/wp-json/wp/v2/...`. CPT צריך `show_in_rest` כדי להופיע |
| **ניהול גרסאות (git)** | רק קוד (התוסף שלנו). **תוכן וחלק מההגדרות יושבים במסד הנתונים, לא ב-git** |

**הבעיה המרכזית בהעברה בין סביבות:** הגדרות שנעשו בממשק (CPTs, שדות, תבניות Elementor) שמורות במסד הנתונים. אין migrations כמו ב-Prisma או Knex. לכן צריך להסכים מראש איך מעבירים אותן (שאלה 3 ברשימה).

## שלב 13. מלכודות נפוצות

1. **שם שדה הוא מחרוזת.** שינוי שם לא נכשל בקומפילציה, הוא פשוט שובר תבנית בשקט. ואין migration אוטומטי: הערכים הישנים נשארים בשם הישן ב-`wp_postmeta`.
2. **כל ערך ב-`postmeta` הוא מחרוזת.** מערכים נשמרים בצורה מסודרת (serialized). השוואה מספרית צריכה לציין סוג.
3. **מטמון בכל מקום:** page cache (LiteSpeed), מטמון CSS של Elementor, מטמון אובייקטים. "שיניתי ולא רואים" הוא כמעט תמיד מטמון.
4. **WP-Cron:** כתבות מתוזמנות (`future`) מתפרסמות על ידי cron שמופעל כשיש ביקור באתר. באתר עם מעט תנועה בשעה מסוימת, פרסום מתוזמן עלול להתעכב. בפרודקשן מקובל להחליף ב-cron אמיתי של השרת.
5. **שמירת permalinks:** אחרי שינוי rewrite חייבים לשמור מחדש, אחרת 404.
6. **סלאגים בעברית:** באתר של המעצב כתבות עם סלאג עברי, שמופיע בכתובת מקודד (`%d7%...`). האזורים באנגלית (`modiin`). צריך להחליט על מדיניות.
7. **תוספים מתנגשים ומתעדכנים.** לנעול גרסאות, ולבדוק ב-staging לפני עדכון.
8. **אבטחה:** כל קלט חייב לעבור סניטציה (`sanitize_text_field`) והדפסה בטוחה (`esc_html`). שאילתות SQL ידניות עם `$wpdb->prepare`. טפסים של תוסף עושים זאת בשבילך, קוד שלנו צריך לעשות זאת בעצמו.
9. **הרשאות:** לא ליצור משתמשי אדמין לכולם. לתת Contributor, Editor לפי הצורך.
10. **תוצאות חיפוש וארכיונים חושפים הכל:** ברירת מחדל, וורדפרס מאנדקס ומציג פריטים שלא תכננת להציג. לבדוק מה ציבורי (`public`, `exclude_from_search`).

## שלב 14. תרגיל ליום הראשון

מטרה: לעבור את כל המסלול בקטן, בסביבת staging.

1. **צור CPT בשם `news`** ב-JetEngine, עם `show_in_rest` פעיל.
2. **הוסף שדות:** `lead` (טקסט) ו-`scope` (בחירה: `national` או `local`).
3. **צור טקסונומיה `area`** (שטוחה, מצורפת ל-`news`, עם rewrite slug `c`) ושלושה מונחים: `modiin`, `holon`, `rishon`.
4. **הוסף 6 כתבות** עם שילובים שונים של `scope` ו-`area`, כולל כתבה בשני אזורים.
5. **בנה Query** ב-Query Builder: סוג `news`, `scope = local`, אזור `modiin`, 5 פריטים, מיון לפי תאריך.
6. **בנה Listing Item ו-Listing Grid** ב-Elementor שמציגים כותרת ופתיח, והצג אותם בדף.
7. **בדוק** ב-Query Monitor איזו שאילתת SQL רצה, ופתח `/wp-json/wp/v2/news` לראות את הנתונים כ-JSON.
8. **שמור permalinks** ובדוק ש-`/c/modiin/` נטען.

אחרי התרגיל תבין את כל הצנרת, ותוכל לקרוא את החוזה כמו מי שבנה אותו.
